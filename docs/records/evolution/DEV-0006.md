# DEV-0006 — Legacy root self-closure / simplification transition

Status: **AUTHORIZED FOR CONTROLLED REGIME ACTIVATION / NOT YET MERGED / POST-MERGE REVALIDATION REQUIRED**

## Contexto

Após o bootstrap merge de CS016E em `main@d20a40d0cd0952d653965b34b67ec30e9ba1b42f`, os dois workflows pós-merge foram observados. `Evolution governance` run `31636170245`, attempt 1, concluiu com sucesso. `Trusted governance root` run `31636170242` falhou no attempt 1 porque o required check `Trusted governance root gate` ainda não estava configurado; após a configuração externa, o mesmo run no attempt 2 concluiu com sucesso. A falha de transição do attempt 1 é preservada e não é reclassificada.

## Achado adicional

A inspeção de `scripts/verify_governance_root.py` mostrou que `current_work()` reconhece um governance amendment somente enquanto sua linha está `in_progress`. O fechamento previsto de CS016E exige mudar essa linha para `accepted` e, simultaneamente, registrar evidências/acceptance chain. Nesse estado candidato, `current_work()` pode retornar nenhum trabalho ativo, enquanto `validate_candidate()` rejeita qualquer diff existente com `candidate changes exist without an active governance amendment or in-progress stage`.

Isso cria um paradoxo de self-closure para a própria camada de governança. Corrigir o verificador root também é bloqueado pela lista steady-state immutable que ele mesmo aplica.

## Decisão de transição

Não mascarar o paradoxo, não criar reviewer fictício e não enfraquecer silenciosamente os checks.

Foi preparada uma transição explícita para uma política menor, baseada no padrão operacional CS001–CS015, com:

- plano de testes congelado antes da campanha;
- resultados individuais obrigatórios;
- `source_sha`, `run_id`, `run_attempt` e workflow exatos;
- verificação pela API oficial do GitHub;
- congelamento de workflow/testes/verificadores declarados;
- qualquer `FAIL`, `SKIPPED`, `NOT_TESTED`, `BLOCKED`, `PARTIAL` ou ausência em teste obrigatório bloqueando validação;
- falhas anteriores preservadas;
- `CI green` explicitamente insuficiente para aceitação.

Em 2026-08-12 o mantenedor declarado autorizou explicitamente a troca de regime. Essa autorização não reclassifica as falhas do root antigo como sucesso e não torna a PR #28 automaticamente aceita. Ela autoriza apenas a execução da janela controlada de transição descrita abaixo.

## Janela administrativa de transição

A política CS016E vigente contém a regra de que um bypass administrativo emergencial deve gerar desvio e invalida aceitação até revalidação. Este documento é o registro do desvio para a troca de regime.

A transição deve obedecer a esta ordem:

1. preservar integralmente os runs antigos que rejeitaram a PR #28;
2. manter `main` protegida contra force-push e deletion, com PR obrigatório e enforcement administrativo;
3. remover temporariamente os required checks antigos apenas durante a janela necessária ao bootstrap do novo workflow, pois `Trusted ChangeSet validation gate` usa `pull_request_target` e só pode ser autoridade confiável depois que o workflow/verificador estiverem presentes na base `main`;
4. mesclar somente a PR #28, no head exato então revisado e publicado;
5. imediatamente após o merge, configurar `Trusted ChangeSet validation gate` como required check estrito da `main`, vinculado ao GitHub Actions app esperado;
6. exigir sucesso do `Main ChangeSet validation` no commit de merge e confirmar que o novo trusted gate passa em uma PR subsequente criada sob o novo regime;
7. até que os itens 5 e 6 sejam demonstrados, a transição permanece **NOT ACCEPTED** e nenhum release ou início de EV-00 é autorizado.

## Limites

A autorização de transição não autoriza:

- apagar ou reescrever CS001–CS016;
- chamar CS016E de aceito sem evidência de fechamento apropriada;
- iniciar CS017/EV-00 antes da estabilização do novo regime;
- liberar produto/release apenas porque a troca de governança foi mesclada;
- usar conta alternativa controlada pelo mesmo mantenedor para simular independência.

## Estado atual

A PR #28 é a candidata de bootstrap do novo regime. A mudança de branch protection é externa ao conteúdo Git e deve ser aplicada deliberadamente. Enquanto isso não ocorrer, a PR permanece bloqueada pelos checks antigos; esse bloqueio é esperado e preservado como evidência da fronteira entre os dois regimes.
