## Context

CS021 has been accepted and protected-integrated, and both mandatory post-merge
gates have passed.

However, the active higher-precedence `audit/STAGE_SCOPE_MAXIMA.json` maximum
for EV-04 was deliberately defined by CS000M around CS021 implementation paths.
It does not authorize the dedicated workflow, validation namespace, ChangeSet
record, decision record or verifier required for a separate administrative
ledger closure.

The CS000M decision explicitly requires a new prospective governance decision
before crossing those boundaries.

## Protected-base manifest anomaly

CS000N preparation also discovered a narrow historical manifest defect in the
accepted CS021 protected merge. The protected `MANIFEST.sha256` contains
exactly two stale rows and no missing or extra rows. The affected paths are the
CS021 lifecycle descriptor and accepted validation result. Their committed LF
blob SHA-256 values are respectively
`9d25d9170e1e3251a66525ea1c0141847318c52c3d9c51a0c124311c373f4214` and
`28a96b7dd7a871508764a2db41591596443d0c856d506442df64a5ac74188921`;
the stale manifest values are respectively
`b1098370c6f36a6b8d9a3ede6c9e0426a616bdf4734dfb81d9c8f34dd48e157b` and
`ebfdf94cf26fe71e32d44388dfbc3bc93aafcb51c98b69096558107e51baa24e`.

The CS000N verifier must prove that converting each protected LF blob to CRLF
reconstructs the stale manifest value exactly. The accepted CS021 evidence and
its protected integration remain immutable; only the current manifest is
prospectively regenerated as part of CS000N.

## Decision

Extend the existing EV-04 maximum with exactly these five additional patterns:

- `.github/workflows/cs000o-ev04-ledger-closure-validation.yml`;
- `audit/validation/CS000O/**`;
- `docs/changesets/000O/**`;
- `docs/records/evolution/DEV-0015.md`;
- `scripts/verify_cs000o_ev04_ledger_closure.py`.

The existing CS021-authorized maximum remains otherwise byte-semantically
unchanged.

## Lifecycle boundary

- EVREQ-016..018 remain `in_progress` with no ledger evidence bound;
