## Finding

The CS019 R1 qualifying workflow was deliberately `pull_request`-triggered.

The permanent Build/CI classifier treats any pull-request workflow containing
configure + build + ctest as CURRENT product regression. Therefore CS019 R1
introduced a second CURRENT product-regression workflow.

`Current product regression` rejected this state at its workflow
classification step with a count of two instead of one.

## Impact analysis

The dedicated CS019 product and contract evidence itself passed:

- all 22 R1 required tests PASS;
- primary build PASS;
- fundamental tests PASS;
- 28/28 smoke tests PASS;
- GCC corpus PASS;
- Clang corpus PASS;
- GCC/Clang byte comparison PASS.

The finding is nevertheless material because accepting the candidate while
ignoring the permanent Build/CI regression would violate `INV-EV-007`.

Changing the frozen R1 workflow or test inventory retroactively would violate
the ChangeSet validation policy.

Therefore R1 cannot be bound as VALIDATED or ACCEPTED.

## Amendment decision

Create CS019 R2 prospectively.

R2 preserves all R1 product bytes and the successful R1 run.

R2 changes only the campaign/control plane needed to classify the dedicated
CS019 workflow as `HISTORICAL_BRANCH`, using an exact-branch push trigger
already supported by the accepted Build/CI classifier.

The accepted permanent classifier is not weakened.

R2 explicitly adds the permanent Build/CI governance checks to its frozen test
inventory.

## Historical failure preservation

Run `32641132506` remains a real failed permanent-governance observation.

Run `32641132555` is preserved separately as
`NOT_APPLICABLE_STALE_SCOPE`: the historical CS000J closure verifier rejected
the expected later EV-02 in-progress lifecycle.

Neither run is deleted, rerun or rewritten.

## Resume condition

Work may resume only after:

1. the R1 nonacceptance record is committed;
2. the R2 plan and workflow are frozen in one source commit;
3. the R2 source contains no product-semantic changes relative to R1;
4. Build/CI workflow classification passes locally against the R2 candidate;
5. the R2 candidate is published once;
6. a new R2 qualifying run executes from that exact source SHA.

No release authorization is granted.
